
Normalmente las solicitudes HTTP GET hacie el endpoint de la API deberian devolver los detalles del usuario solicitado

![[Pasted image 20260724205813.png]]

Como vimos la unica forma de autorizacion en nuestras solicitudes HTTP es por medio del role ya que no hay otra forma de autenticacion como Tokens. Incluso si hubiera un token, el sistema de control del backend deberia comaparar activamente este con los detalles del objeto solicitado

## Modificacion de los detalles de otro usuario

Una vez conocemos su uuid podemos cambiar nuestra solicitud HTTP PUT con el uid, uuid y role del usuario 2 y cambiar los detalles de fullname, email y about si quisieramos:

![[Pasted image 20260724210154.png]]

No recibimos mensaje de error y si volvemos a hacer un GET al usuario 2 veremos que los datos han cambiado:

![[Pasted image 20260724210223.png]]

Se podria cambiar el email del usuario, pedir un cambio de contraseña y que se envie a nuestro email, colocar un XSS en el campo about que nos de sus cookies cuando entre...

## Ejemplo practico

Trata de cambiar el admin email a `flag@idor.htb` y deberias obtener la flag en la pagina editar profile

1. Con la solicitud HTTP GET de antes la mandamos al Intruder (el GET nos permitia ver los datos de otros usuarios)

![[Pasted image 20260724211349.png]]

2. Ahi ponemos el puntero tanto en la URL de llamada a API como en el JSON. Ponemos el payload de numeros hasta 20 y ponemos que matchee los resultados con admin, adm o administrator

![[Pasted image 20260724211426.png]]![[Pasted image 20260724211524.png]]

3. Encontramos un match y vemos que el role es `staff_admin`, ademas vemos el uuid del admin y su uid

![[Pasted image 20260724211555.png]]

4. Cambiamos el email del admin desde el Repeater usando el uid 10, el uuid encontrado y el role staff_admin ademas de poner el metodo HTTP PUT, y vemos que no nos da error

![[Pasted image 20260724211752.png]]
![[Pasted image 20260724212031.png]]

5. Recargamos la pagina normal donde esta nuestro edit profile y vemos la flag
