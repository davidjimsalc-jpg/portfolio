
## Kerberoasting entre Bosques (Cross-Forest)

Los ataques de Kerberos como el Kerberoasting y el ASREPRoasting se pueden realizar a través de las confianzas, dependiendo de la dirección de la confianza

Si la confianza es desde un bosque/dominio entrante o bidireccional es probable que podamos realizar varios ataques

Podriamos obtener un ticket Kerberos, romper el hash para un usuario administrativo o que tenga privs Enterprise Admin en los dos dominios


1. Usamos PowerView para enumerar cuentas en un dominio objetivo que tiene varios SPNs

```
Get-DomainUser -SPN -Domain FREIGHTLOGISTICS.LOCAL | select SamAccountName
```
![[Pasted image 20261005174135.png]]

	Vemos una cuenta con SPN en el dominio objetivo

2. Comprobando la cuenta

```
Get-DomainUser -Domain FREIGHTLOGISTICS.LOCAL -Identity mssqlsvc |select samaccountname,memberof
```

	Esta comprobacion nos muestra que es un Domain Admin en el dominio objetivo por lo que si podemos hacer Kerberoasting y romper su hash tendriamos derechos admin

3. Realizamos el ataque Kerberoasting con Rubeus usando /domain

```
.\Rubeus.exe kerberoast /domain:FREIGHTLOGISTICS.LOCAL /user:mssqlsvc /nowrap
```
![[Pasted image 20261005174326.png]]


## Reutilizacion de contraseñas de administrador y pertenencia a grupos

Hay veces que podemos encontrar una confianza de bosque bidireccional gestionada por administradores de la misma empresa

Si tomamos control de DOMINIO A y obtenemos las contraseñas en texto claro o hashes NT para la cuenta Administrator del DOMINIO A y el DOMINIO B tiene una cuenta admin con el mismo nombre podriamos comprobar si hay reutilizacion de contraseñas

Ejemplo:
- DOMINIO A: adm_bob.smith
- DOMINIO B: bsmith_admin

También podemos ver usuarios o administradores del Dominio A como miembros de un grupo en el Dominio B. Solo los `Grupos Locales de Dominio` (Domain Local Groups) permiten entidades de seguridad (security principals) de fuera de su bosque

Podemos ver a un Administrador de Dominio o Administrador de la Empresa del Dominio A como miembro del grupo de Administradores integrado en el Dominio B en una relación de confianza de bosque bidireccional. Si podemos tomar el control de este usuario administrador en el Dominio A, obtendríamos acceso administrativo completo al Dominio B basándonos en la pertenencia al grupo


1. PowerView [Get-DomainForeignGroupMember](https://powersploit.readthedocs.io/en/latest/Recon/Get-DomainForeignGroupMember/) para enumerar grupos con usuarios que no pertenecen al dominio y son pertenencia a un grupo externo (foreign group membership)

```
Get-DomainForeignGroupMember -Domain FREIGHTLOGISTICS.LOCAL
```
![[Pasted image 20261005175035.png]]

	La salida del comando anterior muestra que el grupo de Administradores integrado en `FREIGHTLOGISTICS.LOCAL` tiene como miembro a la cuenta de Administrador integrada del dominio `INLANEFREIGHT.LOCAL`


2. Verificamos acceso a DC01 usando Enter-PSSession

```
Enter-PSSession -ComputerName ACADEMY-EA-DC03.FREIGHTLOGISTICS.LOCAL -Credential INLANEFREIGHT\administrator
```
![[Pasted image 20261005175142.png]]


	En la salida del comando anterior, podemos ver que nos autenticamos con éxito en el Controlador de Dominio del dominio `FREIGHTLOGISTICS.LOCAL` usando la cuenta de Administrador del dominio `INLANEFREIGHT.LOCAL` a través de la confianza de bosque bidireccional


## Abuso de sidHistory entre bosques

Ataque ExtraSids

El Historial de SID (SID History) también puede ser abusado a través de una confianza de bosque. Si un usuario es migrado de un bosque a otro y el Filtrado de SID (SID Filtering) no está habilitado, es posible añadir un SID del otro bosque, y este SID se añadirá al token del usuario al autenticarse a través de la confianza

Si el SID de una cuenta con privilegios administrativos en el Bosque A se añade al atributo de historial de SID de una cuenta en el Bosque B, suponiendo que puedan autenticarse a través del bosque, entonces esta cuenta tendrá privilegios administrativos al acceder a los recursos en el bosque asociado

En el siguiente diagrama, podemos ver un ejemplo del usuario `jjones` siendo migrado del dominio `INLANEFREIGHT.LOCAL` al dominio `CORP.LOCAL` en un bosque diferente. Si el filtrado de SID no está habilitado cuando se realiza esta migración y el usuario tiene privilegios administrativos en el dominio `INLANEFREIGHT.LOCAL`, entonces conservará sus derechos/acceso administrativo en `INLANEFREIGHT.LOCAL` mientras es miembro del nuevo dominio, `CORP.LOCAL`, en el segundo bosque
