## Pertenencia a grupos relacionados con Exchange

A Exchange se le suelen conceder privilegios dentro del dominio. El grupo `Exchange Windows Permissions` no es un grupo protegido pero a sus miembros se les concede la capacidad de escribir una DACL

Podemos dar permisos DCSync a un usuario, añadir cuentas a este grupo aprovechando una DACL o una cuenta comprometida que sea miembtro de Account Operators

Este [repositorio de GitHub](https://github.com/gdedrouas/Exchange-AD-Privesc) detalla algunas técnicas para aprovechar Exchange para escalar privilegios en un entorno de AD

Otro grupo importante es `Exchange Organization Management` (son los Domain Admins de Exchange) y puede acceder a los buzones de correo de todos los usuarios. Tiene control total sobre la OU `Microsoft Exchange Security Groups` que conteien el grupo `Exchange Windows Permissions`

- Ver los permisos de Organization Management

![[Pasted image 20260929190741.png]]

Si podemos comprometer un servidor de Exchange, esto a menudo nos llevará a obtener privilegios de Domain Admin. Además, el volcado de credenciales en memoria desde un servidor de Exchange producirá decenas, si no cientos, de credenciales en texto plano o hashes NTLM. Esto se debe a menudo a que los usuarios inician sesión en Outlook Web Access (OWA) y Exchange almacena en caché sus credenciales en memoria tras un inicio de sesión exitoso


## PrivExchange

El ataque `PrivExchange` es el resultado de un fallo en la característica `PushSubscription` de Exchange Server, que permite a cualquier usuario del dominio con un buzón de correo forzar al servidor de Exchange a autenticarse en cualquier host proporcionado por el cliente a través de HTTP

El servicio de Exchange se ejecuta como SYSTEM y tiene privilegios excesivos por defecto

Este fallo se puede aprovechar para retransmitir a LDAP (relay to LDAP) y volcar la base de datos NTDS del dominio. Si no podemos retransmitir a LDAP, esto se puede aprovechar para retransmitir y autenticarse en otros hosts dentro del dominio


## Printer Bug

Fallo en el protocolo MS-RPRN. Este protocolo define la comunicación del procesamiento de trabajos de impresión y la gestión del sistema de impresión entre un cliente y un servidor

Para aprovechar este fallo, cualquier usuario del dominio puede conectarse a la tubería con nombre del administrador de trabajos de impresión (spooler) con el método `RpcOpenPrinter` y utilizar el método `RpcRemoteFindFirstPrinterChangeNotificationEx`, y forzar al servidor a autenticarse en cualquier host proporcionado por el cliente a través de SMB

El servicio de cola de impresión (spooler) se ejecuta como SYSTEM y se instala por defecto en los servidores de Windows que ejecutan Desktop Experience

Este ataque se puede aprovechar para retransmitir a LDAP y otorgar a tu cuenta de atacante privilegios DCSync para recuperar todos los hashes de contraseñas de AD.

Como se conserva en [este](https://github.com/itzvenom/Security-Assessment-PS) repositorio o en [esta](https://github.com/NotMedic/NetNTLMtoSilverTicket) herramienta para comprobar si las máquinas son vulnerables al [MS-PRN Printer Bug](https://blog.sygnia.co/demystifying-the-print-nightmare-vulnerability). Este fallo puede utilizarse para comprometer un host en otro bosque que tenga habilitada la Delegación no restringida (Unconstrained Delegation), como un controlador de dominio

```
Import-Module .\SecurityAssessment.ps1
Get-SpoolStatus -ComputerName ACADEMY-EA-DC01.INLANEFREIGHT.LOCAL
```

## MS14-068

Fallo en el protocolo Kerberos que podía aprovecharse junto con las credenciales de un usuario de dominio estándar para elevar privilegios a Domain Admin

Un ticket de Kerberos contiene la pertenencia a grupos en el Certificado de Atributos de Privilegio o PAC). El PAC está firmado por el KDC utilizando claves secretas para validar que el PAC no ha sido manipulado después de su creación

La vulnerabilidad permitía que un PAC falsificado fuera aceptado por el KDC como legítimo. Esto puede aprovecharse para crear un PAC falso, presentando a un usuario como miembro de los Domain Administrators u otro grupo privilegiado. Puede ser explotado con herramientas como el [Python Kerberos Exploitation Kit (PyKEK)](https://github.com/SecWiki/windows-kernel-exploits/tree/master/MS14-068/pykek)

La máquina [Mantis](https://app.hackthebox.com/machines/98) en la plataforma Hack The Box muestra esta vulnerabilidad.


## Captura de credenciales LDAP

Muchas aplicaciones e impresoras almacenan credenciales LDAP en su consola de administración web para conectarse al dominio. A menudo, estas consolas se dejan con contraseñas débiles

A veces, estas credenciales se pueden ver en texto plano. Otras veces, la aplicación tiene una función de `probar conexión` que podemos utilizar para obtener credenciales cambiando la dirección IP del servidor LDAP a la de nuestro host de ataque y configurando un listener de `netcat` en el puerto LDAP 389

Cuando el dispositivo intente probar la conexión LDAP, enviará las credenciales a nuestra máquina, a menudo en texto plano. Las cuentas utilizadas para las conexiones LDAP suelen tener privilegios, pero si no, esto podría servir como un punto de apoyo inicial

## Enumeración de registros DNS

Podemos usar una herramienta como [adidnsdump](https://github.com/dirkjanm/adidnsdump) para enumerar todos los registros DNS en un dominio usando una cuenta de usuario de dominio válida. Esto es especialmente útil si la convención de nombres para los hosts que nos devuelven nuestras enumeraciones con herramientas como `BloodHound` es similar a `SRV01934.INLANEFREIGHT.LOCAL`. ## Campo PASSWD_NOTREQD

Es posible encontrar cuentas de dominio con el campo [passwd_notreqd](https://ldapwiki.com/wiki/Wiki.jsp?page=PASSWD_NOTREQD) establecido en el atributo userAccountControl. Si está establecido, el usuario no está sujeto a la longitud de la política de contraseñas actual, lo que significa que podría tener una contraseña más corta o ninguna

```
Get-DomainUser -UACFilter PASSWD_NOTREQD | Select-Object samaccountname,useraccountcontrol
```

## Contraseñas de Preferencias de Directiva de Grupo (GPP)

Cuando se crea una nueva GPP, se crea un archivo .xml en el recurso compartido SYSVOL, que también se almacena en caché localmente en los puntos finales a los que se aplica la Directiva de Grupo. Estos archivos pueden incluir los utilizados para:

- Mapear unidades (drives.xml)
- Crear usuarios locales
- Crear archivos de configuración de impresoras (printers.xml)
- Crear y actualizar servicios (services.xml)
- Crear tareas programadas (scheduledtasks.xml)
- Cambiar contraseñas de administrador local.

Estos archivos pueden contener una variedad de datos de configuración y contraseñas definidas

El valor del atributo `cpassword` está cifrado con AES de 256 bits, pero Microsoft [publicó la clave privada AES en MSDN](https://docs.microsoft.com/en-us/openspecs/windows_protocols/ms-gppref/2c15cbf0-f086-4c74-8b70-1f2fa45dd4be?redirectedfrom=MSDN), que puede usarse para descifrar la contraseña

El parche no elimina los archivos Groups.xml existentes con contraseñas de SYSVOL. Si eliminas la directiva GPP en lugar de desvincularla de la OU, la copia en caché en el equipo local permanece.

El XML tiene el siguiente aspecto:

![[Pasted image 20260929192422.png]]

Si recuperas el valor de cpassword de forma más manual, la utilidad `gpp-decrypt` se puede utilizar para descifrar la contraseña de la siguiente manera:

```
gpp-decrypt VPe/o9YRyz2cksnYRbNeQj35w9KxQ5ttbvtRaAVqxaE
```
![[Pasted image 20260929192443.png]]

Las contraseñas de GPP se pueden localizar buscando o navegando manualmente por el recurso compartido SYSVOL o utilizando herramientas como [Get-GPPPassword.ps1](https://github.com/PowerShellMafia/PowerSploit/blob/master/Exfiltration/Get-GPPPassword.ps1). CrackMapExec también tiene dos módulos para localizar y recuperar contraseñas de GPP

```
crackmapexec smb -L | grep gpp
```
![[Pasted image 20260929192530.png]]

	A menudo, las contraseñas de GPP se definen para cuentas heredadas y, por lo tanto, puedes recuperar y descifrar la contraseña de una cuenta bloqueada o eliminada. Sin embargo, vale la pena intentar hacer un password spraying interno



También es posible encontrar contraseñas en archivos como Registry.xml cuando el inicio de sesión automático (autologon) está configurado a través de una Directiva de Grupo

Si esto se establece a través de una Directiva de Grupo y no localmente en el host, entonces cualquiera en el dominio puede recuperar las credenciales almacenadas en el archivo Registry.xml creado para este propósito

Podemos buscar esto usando CrackMapExec con el módulo [gpp_autologin](https://www.infosecmatter.com/crackmapexec-module-library/?cmem=smb-gpp_autologin), o usando el script [Get-GPPAutologon.ps1](https://github.com/PowerShellMafia/PowerSploit/blob/master/Exfiltration/Get-GPPAutologon.ps1)

```
crackmapexec smb 172.16.5.5 -u forend -p Klmcargo2 -M gpp_autologin
```

En la salida anterior, podemos ver que hemos recuperado las credenciales de una cuenta llamada `guarddesk`. Esto podría haberse configurado para que las estaciones de trabajo compartidas utilizadas por los guardias inicien sesión automáticamente al arrancar para acomodar a múltiples usuarios a lo largo del día y la noche


## ASREPRoasting

Es posible obtener el Ticket de Otorgamiento de Tickets (Ticket Granting Ticket o TGT) para cualquier cuenta que tenga habilitada la configuración `No requerir la preautenticación Kerberos` ([Do not require Kerberos pre-authentication](https://www.tenable.com/blog/how-to-stop-the-kerberos-pre-authentication-attack-in-active-directory))

Con la preautenticación, un usuario introduce su contraseña, que cifra una marca de tiempo. El Controlador de Dominio la descifrará para validar que se utilizó la contraseña correcta. Si tiene éxito, se emitirá un TGT

Si una cuenta tiene la preautenticación deshabilitada, un atacante puede solicitar datos de autenticación para la cuenta afectada y recuperar un TGT cifrado del Controlador de Dominio

#### Viendo una cuenta con la opción No requerir preautenticación Kerberos

![[Pasted image 20260929192919.png]]


ASREPRoasting es similar a Kerberoasting, pero implica atacar la AS-REP en lugar de la TGS-REP. No se requiere un SPN

El ataque en sí puede realizarse con el kit de herramientas [Rubeus](https://github.com/GhostPack/Rubeus). Si un atacante tiene permisos `GenericWrite` o `GenericAll` sobre una cuenta, puede habilitar este atributo y obtener el ticket AS-REP para el descifrado sin conexión

#### Recuperando la AS-REP usando Rubeus Windows

1. Se puede usar PowerView para enumerar usuarios con su valor de UAC establecido en `DONT_REQ_PREAUTH`

```
Get-DomainUser -PreauthNotRequired | select samaccountname,userprincipalname,useraccountcontrol | fl
```
![[Pasted image 20260929193050.png]]

2. Rubeus puede ser aprovechada para recuperar la AS-REP en el formato adecuado para el descifrado de hashes sin conexión. Este ataque no requiere ningún contexto de usuario de dominio y se puede hacer simplemente conociendo el nombre SAM del usuario sin preautenticación Kerberos. Recuerda, añade el indicador `/nowrap` para que el ticket no se ajuste a la columna

```
.\Rubeus.exe asreproast /user:mmorgan /nowrap /format:hashcat
```
![[Pasted image 20260929193143.png]]

3. Descifrando el hash sin conexión con Hashcat

```
hashcat -m 18200 ilfreight_asrep /usr/share/wordlists/rockyou.txt
```
![[Pasted image 20260929193210.png]]

#### Recuperando la AS-REP usando Kerbrute Linux

Al realizar la enumeración de usuarios con `Kerbrute`, la herramienta recuperará automáticamente la AS-REP para cualquier usuario encontrado que no requiera preautenticación Kerberos

```
kerbrute userenum -d inlanefreight.local --dc 172.16.5.5 /opt/jsmith.txt
```
![[Pasted image 20260929193246.png]]

Con una lista de usuarios válidos, podemos usar [Get-NPUsers.py](https://github.com/SecureAuthCorp/impacket/blob/master/examples/GetNPUsers.py) para buscar todos los usuarios que no requieren preautenticación Kerberos. La herramienta recuperará la AS-REP en formato Hashcat para el descifrado

#### Búsqueda de usuarios con preautenticación de Kerberos no requerida

```
GetNPUsers.py INLANEFREIGHT.LOCAL/ -dc-ip 172.16.5.5 -no-pass -usersfile valid_ad_users
```

## Abuso de Objetos de Directiva de Grupo (GPO)

La Directiva de Grupo (Group Policy) proporciona a los administradores muchas configuraciones avanzadas que se pueden aplicar tanto a objetos de usuario como de equipo en un entorno de AD

Si podemos obtener permisos sobre un Objeto de Directiva de Grupo a través de una mala configuración de ACL, podríamos aprovecharlo para el movimiento lateral, la escalada de privilegios, el compromiso del dominio e incluso como un mecanismo de persistencia

Las malas configuraciones de GPO pueden ser abusadas para realizar los siguientes ataques:

- Añadir permisos adicionales a un usuario (como `SeDebugPrivilege`, `SeTakeOwnershipPrivilege` o `SeImpersonatePrivilege`)
- Añadir un usuario administrador local a uno o más hosts
- Crear una tarea programada inmediata para realizar cualquier número de acciones

Podemos enumerar la información de los GPO utilizando muchas de las herramientas que hemos estado usando a lo largo de este módulo, como PowerView y BloodHound. También podemos usar [group3r](https://github.com/Group3r/Group3r), [ADRecon](https://github.com/sense-of-security/ADRecon), [PingCastle](https://www.pingcastle.com/)

#### Enumerar nombres de GPO con PowerView

```
Get-DomainGPO |select displayname
```
![[Pasted image 20260929193750.png]]

Podemos ver que se está usando el inicio de sesión automático (autologon), lo que puede significar que hay una contraseña legible en un GPO, y vemos que los Servicios de Certificados de Active Directory (AD CS) están presentes en el dominio. 

Si las Herramientas de Administración de Directivas de Grupo (Group Policy Management Tools) están instaladas en el host desde el que estamos trabajando, podemos usar varios [cmdlets de GroupPolicy](https://docs.microsoft.com/en-us/powershell/module/grouppolicy/?view=windowsserver2022-ps) incorporados, como `Get-GPO`, para realizar la misma enumeración

#### Enumerar nombres de GPO con un cmdlet incorporado

```
Get-GPO -All | Select DisplayName
```
![[Pasted image 20260929193900.png]]

A continuación, podemos comprobar si un usuario que controlamos tiene algún permiso sobre un GPO

#### Enumerar los permisos de GPO de los usuarios del dominio

```
$sid=Convert-NameToSid "Domain Users"
Get-DomainGPO | Get-ObjectAcl | ?{$_.SecurityIdentifier -eq $sid}
```
![[Pasted image 20260929193950.png]]

Aquí podemos ver que el grupo Domain Users tiene varios permisos sobre un GPO, como `WriteProperty` y `WriteDacl`, que podríamos aprovechar para darnos control total sobre el GPO y llevar a cabo cualquier número de ataques que se aplicarían a todos los usuarios y equipos en las OU a las que se aplica el GPO. Podemos usar el GUID del GPO combinado con `Get-GPO` para ver el nombre de visualización (display name) del GPO.

#### Convertir el GUID de un GPO a su nombre

```
Get-GPO -Guid 7CA9C789-14CE-46E3-A722-83F4097AF532
```
![[Pasted image 20260929194030.png]]

Al comprobar en BloodHound, podemos ver que el grupo `Domain Users` tiene varios permisos sobre el GPO `Disconnect Idle RDP`, lo que podría ser aprovechado para obtener el control total del objeto

![[Pasted image 20260929194050.png]]

Si seleccionamos el GPO en BloodHound y nos desplazamos hacia abajo hasta `Affected Objects` en la pestaña `Node Info`, podemos ver que este GPO se aplica a una OU, que contiene cuatro objetos de equipo.

![[Pasted image 20260929194116.png]]

Podríamos usar una herramienta como [SharpGPOAbuse](https://github.com/FSecureLABS/SharpGPOAbuse) para aprovechar esta mala configuración del GPO realizando acciones como añadir un usuario que controlamos al grupo de administradores locales en uno de los hosts afectados, crear una tarea programada inmediata en uno de los hosts para darnos una reverse shell, o configurar un script de inicio de equipo malicioso para proporcionarnos una reverse shell o algo similar
