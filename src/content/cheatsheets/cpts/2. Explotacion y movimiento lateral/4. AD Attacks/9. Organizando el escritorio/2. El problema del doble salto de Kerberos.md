
Surge cuando un atacante intenta usar autenticacion Kerberos a traves de dos o mas saltos. El problema esta en como se conceden los tickets:

	Los tickets son fragmentos firmados por el KDC que indican los recursos que puede acceder una cuenta. Con kerberos al autenticarnos nos da un ticket para acceder a ese objeto y con hashes NTLM se guarda en nuestra sesion

## Antecedentes

Suele ocurrir cuando se usa WinRM/Powershell ya que el mecanismo de autenticacion solo proporciona un ticket para acceder a un recurso especifico lo que causara problemas en movimientos laterales

En esta situacion la cuenta de usuario que se esta usando tiene los derechos para realizar la accion pero se le estan negando

El quid esta en que cuando usamos WinRM con Kerberos, este no se guarda en la cache. Si lo hacemos con hashes NTLM este se almacena en la sesion para acceder a otros recursos posteriores

#### Ejemplo 

Nos conectamos via WinRM y usamos Mimikatz. No vemos nuestra cred del usuario backupadm en memoria

```
Enter-PSSession -ComputerName DEV01 -Credential INLANEFREIGHT\backupadm
cd 'C:\Users\Public\'
.\mimikatz "privilege::debug" "sekurlsa::logonpasswords" exit
```
![[Pasted image 20260929164702.png]]

Efectivamente, hay procesos que se ejecutan en el contexto del usuario `backupadm`, como `wsmprovhost.exe`, que es el proceso que se genera cuando se inicia una sesión remota de Windows PowerShell.

```
tasklist /V |findstr backupadm
```
![[Pasted image 20260929164731.png]]

En los términos más simples, en esta situación, cuando intentamos emitir un comando multiservidor, nuestras credenciales no se enviarán desde la primera máquina a la segunda


Supongamos que tenemos tres hosts: `Host de ataque` --> `DEV01` --> `DC01`. Nuestro host de ataque es una máquina Parrot dentro de la red corporativa, pero no está unida al dominio. Obtenemos un conjunto de credenciales para un usuario de dominio y descubrimos que forma parte del grupo `Remote Management Users` en DEV01. Queremos utilizar `PowerView` para enumerar el dominio, lo que requiere comunicación con el controlador de dominio (Domain Controller), DC01.


![[Pasted image 20260929164842.png]]

Cuando nos conectamos a `DEV01` utilizando una herramienta como `evil-winrm`, nos conectamos con autenticación de red, por lo que nuestras credenciales no se almacenan en la memoria y, por lo tanto, no estarán presentes en el sistema para autenticarse en otros recursos en nombre de nuestro usuario

Esto sucede porque el ticket TGT (Ticket Granting Ticket) de Kerberos del usuario no se envía a la sesión remota; por lo tanto, el usuario no tiene forma de probar su identidad y los comandos ya no se ejecutarán en el contexto de este usuario

Al autenticarse en el host objetivo, el ticket del servicio de concesión de tickets (TGS) del usuario se envía al servicio remoto, lo que permite la ejecución de comandos, pero el ticket TGT del usuario no se envía. Cuando el usuario intenta acceder a recursos posteriores en el dominio, su TGT no estará presente


## Soluciones alternativas

#### Solución alternativa n.º 1: Objeto PSCredential

También podemos conectarnos al host remoto a través del host A y configurar un objeto PSCredential para pasar nuestras credenciales nuevamente

1. Después de conectarnos a un host remoto con credenciales de dominio

```
import-module .\PowerView.ps1
```
![[Pasted image 20260929165133.png]]

	Como se ve a continuación, obtenemos un error porque no podemos pasar nuestra autenticación al controlador de dominio para consultar las cuentas SPN

2. Si verificamos con `klist`, vemos que solo tenemos un ticket de Kerberos en caché para nuestro servidor actual.

```
klist
```
![[Pasted image 20260929165213.png]]


3. Así que ahora, configuremos un objeto PSCredential e intentemos de nuevo. Primero, configuramos nuestra autenticación.

```
$SecPassword = ConvertTo-SecureString '!qazXSW@' -AsPlainText -Force
```
![[Pasted image 20260929165240.png]]

4. Ahora podemos intentar consultar las cuentas SPN usando PowerView y tenemos éxito

```
get-domainuser -spn -credential $Cred | select samaccountname
```
![[Pasted image 20260929165303.png]]

5. Si nos conectamos por RDP al mismo host, abrimos un CMD y escribimos `klist`, veremos que tenemos los tickets necesarios en caché para interactuar directamente con el controlador de dominio, y no tenemos que preocuparnos por el problema del doble salto

```
klist
```
![[Pasted image 20260929165403.png]]


#### Solución alternativa n.º 2: Registrar la configuración de PSSession

Qué pasa si estamos en un host unido al dominio y podemos conectarnos de forma remota a otro usando WinRM? ¿O si estamos trabajando desde un host de ataque de Windows y nos conectamos a nuestro objetivo a través de WinRM usando el [cmdlet Enter-PSSession](https://docs.microsoft.com/en-us/powershell/module/microsoft.powershell.core/enter-pssession?view=powershell-7.2)?


1. Establecer primero una sesión de WinRM en el host remoto

```
Enter-PSSession -ComputerName ACADEMY-AEN-DEV01.INLANEFREIGHT.LOCAL -Credential inlanefreight\backupadm
```
![[Pasted image 20260929165523.png]]

2. Si verificamos los tickets en caché usando `klist`, veremos que el mismo problema existe. Debido al problema del doble salto, solo podemos interactuar con los recursos en nuestra sesión actual, pero no podemos acceder directamente al DC usando PowerView. Podemos ver que nuestro TGS actual es válido para acceder al servicio HTTP en el objetivo, ya que nos conectamos a través de WinRM, que utiliza solicitudes SOAP

```
klist
```
![[Pasted image 20260929165626.png]]

3. Tampoco podemos interactuar directamente con el DC usando PowerView

```
Import-Module .\PowerView.ps1
get-domainuser -spn | select samaccountname
```
![[Pasted image 20260929165650.png]]

4. Un truco que podemos usar aquí es registrar una nueva configuración de sesión usando el cmdlet [Register-PSSessionConfiguration](https://docs.microsoft.com/en-us/powershell/module/microsoft.powershell.core/register-pssessionconfiguration?view=powershell-7.2).

```
Register-PSSessionConfiguration -Name backupadmsess -RunAsCredential inlanefreight\backupadm
```
![[Pasted image 20260929165728.png]]

5. Una vez hecho esto, necesitamos reiniciar el servicio WinRM escribiendo `Restart-Service WinRM` en nuestra PSSession actual. Esto nos expulsará, así que iniciaremos una nueva PSSession usando la sesión registrada con nombre que configuramos previamente.

6. Después de iniciar la sesión, podemos ver que el problema del doble salto ha sido eliminado, y si escribimos `klist`, tendremos los tickets en caché necesarios para llegar al controlador de dominio. Esto funciona porque nuestra máquina local ahora se hará pasar por la máquina remota en el contexto del usuario `backupadm` y todas las solicitudes de nuestra máquina local se enviarán directamente al controlador de dominio.

```
Enter-PSSession -ComputerName DEV01 -Credential INLANEFREIGHT\backupadm -ConfigurationName backupadmsess

klist
```
![[Pasted image 20260929165832.png]]

7. Ahora podemos ejecutar herramientas como PowerView sin tener que crear un nuevo objeto PSCredential.

```
get-domainuser -spn | select samaccountname
```
